# Architecture — Financial Risk & Fraud Detection Data Platform

## 1. Overview

This platform simulates a mid-to-large financial company processing millions of transactions per day. The architecture follows a **Lambda-style hybrid pattern**, combining:

- A **batch layer** for historical, reliable, end-of-day processing
- A **streaming layer** for near-real-time risk scoring and fraud alerting
- A **serving layer** (BigQuery + Looker Studio) for analytics and dashboards

The platform is designed to be **production-grade**, **cost-aware**, and **operationally observable**. Every architectural decision is justified in the context of the Google Professional Data Engineer (PDE) exam and real-world enterprise data engineering.

## 3. Component Descriptions

### 3.1 Data Sources

| Source | Type | Description |
|---|---|---|
| PostgreSQL | OLTP database | Historical customers, accounts, merchants, devices, transactions |
| REST APIs | External HTTP | Currency exchange rates, merchant metadata enrichment |
| Event stream | Real-time | Transactions generated by an application and ingested via Cloud Run → Pub/Sub |

### 3.2 Batch Ingestion

1. **Cloud Composer DAG** triggers daily at 02:00 UTC
2. Python ingestion scripts extract from PostgreSQL using incremental watermarks
3. Files are uploaded to `gs://<bucket>/raw/<entity>/<date>/`
4. A Dataflow batch job reads Avro/CSV, validates, transforms, and writes to BigQuery

### 3.3 Streaming Ingestion

1. An application (or event generator script) POSTs transaction events to the **Cloud Run** ingestion API
2. Cloud Run publishes messages to the `transaction-events` **Pub/Sub** topic
3. A Dataflow streaming pipeline continuously reads from the subscription:
   - Parses and validates messages
   - Enriches with dimension lookups (side inputs from BigQuery / GCS)
   - Applies 5-minute fixed windows for velocity feature aggregation
   - Calculates a real-time risk score (0–100)
   - Writes to BigQuery via the Storage Write API
   - Routes malformed messages to the `transaction-dead-letter` topic

### 3.4 BigQuery Layered Architecture

```
BigQuery
├── raw          — landing zone; raw data as received, no transformations
├── staging      — typed, cleaned, deduplicated; schema validated
├── core         — dimensional model (star schema): dim_* + fact_*
└── analytics    — business-level marts: risk scores, summaries, KPIs
```

### 3.5 Orchestration (Airflow / Cloud Composer)

All batch workflows are orchestrated by Apache Airflow deployed on Cloud Composer 2.

Key DAGs:
- `batch_ingestion_dag` — extract → GCS → Dataflow → BQ raw/staging
- `dimension_refresh_dag` — SCD Type 2 merge for dim_customer, dim_merchant
- `fact_load_dag` — fact_transaction, fact_transaction_event loads
- `data_quality_dag` — Great Expectations checkpoints after each layer
- `analytics_mart_dag` — refresh analytics tables
- `monitoring_dag` — data freshness + volume anomaly checks

### 3.6 Cloud Run (Transaction Ingestion API)

A small FastAPI application deployed to Cloud Run (serverless) that:
- Accepts `POST /transactions` with a JSON payload
- Validates the payload (Pydantic models)
- Publishes to Pub/Sub
- Returns `202 Accepted` immediately (async)
- Scales to zero when idle (cost-efficient)

### 3.7 Security Model

| Component | Service Account | Permissions |
|---|---|---|
| Cloud Run | `cloudrun-sa@` | `pubsub.publisher` on `transaction-events` |
| Dataflow | `dataflow-sa@` | `storage.objectViewer`, `bigquery.dataEditor` |
| Airflow | `composer-sa@` | `bigquery.dataEditor`, `dataflow.developer`, `storage.objectAdmin` |
| BigQuery users | `analytics-sa@` | `bigquery.dataViewer` on `analytics` dataset only |

All secrets (DB passwords, API keys) are stored in **Cloud Secret Manager**. No plaintext credentials anywhere.

## 4. Why Lambda Architecture (Not Kappa)?

| Dimension | Lambda (this project) | Kappa (streaming only) |
|---|---|---|
| Historical reprocessing | ✅ Simple — rerun batch job | ❌ Complex — replay entire stream |
| Latency | Batch: minutes–hours; Stream: seconds | Seconds only |
| Operational complexity | Moderate (two code paths) | Lower (one code path) |
| Cost | Lower (batch runs off-peak) | Higher (always-on streaming) |
| BigQuery compatibility | ✅ Excellent | ✅ Good (streaming inserts cost more) |

For a financial platform with both historical analytics AND real-time fraud detection, Lambda is the pragmatic choice. The cost savings from running batch jobs off-peak (slot pricing vs. on-demand) are significant at scale.

## 5. BigQuery Performance Design

All fact tables are:
- **Partitioned by `transaction_date`** (DATE column derived from `transaction_timestamp`)
- **Clustered by `customer_id`, `merchant_id`**

This means a query like:
```sql
SELECT * FROM core.fact_transaction
WHERE transaction_date = '2024-01-15'
  AND customer_id = '...'
```
...scans **only the relevant partition + cluster**, not the full table. At 500M+ rows, this reduces bytes processed by 99%+.

## 6. Disaster Recovery & Data Retention

| Storage Layer | Retention | Backup Strategy |
|---|---|---|
| GCS raw bucket | 90 days (lifecycle rule) | Raw data is the backup |
| GCS archive | 365 days | Nearline/Coldline storage class |
| BigQuery | Table snapshots every 7 days | BQ time travel (7 days default) |
| PostgreSQL | Docker volume | pg_dump nightly (local dev only) |
